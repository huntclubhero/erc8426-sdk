# Changelog

## 0.3.1 (issuer only)

Two fixes to the identical-repeat handling introduced in 0.3.0, found by the hosted demo's smoke run.

- `@erc8426/issuer`: a repeat no longer masks a transfer. On `POST /links/:link` the link is resolved and the fresh entitlement read is taken BEFORE the repeat store is consulted, and the read's result is part of the repeat key, so an identical repeat after the token changed hands (before any rotation has been observed) is a new request and meets the fresh read: 403 `not_owner`, not the recorded 200. A read that cannot be taken answers 503 without touching the store. The read is taken once per request and reused by the handler. `POST /:tokenId/actions/:action` keys by the fresh read for the challenge's claimed account the same way (`AuthorizeInput.freshRead` lets `authorize` reuse it), so a repeat after a transfer is judged afresh; the nonce it spent makes that `nonce_invalid`.
- `@erc8426/issuer`: deliberate taps stay distinct. The built-in confirm page (`defaultConfirmPage`) carries a fresh random hidden `attempt` field per render (`newAttempt`), so a page-driven POST is unique per tap and executes each time, while the browser's aborted-and-resent POST of the same page (same body) is still coalesced into one execution. Integrators that POST a link directly and want repeats to count send a per-tap `attempt` (or any distinguishing body member); an identical immediate re-POST is the same request by design. `repeat.windowSeconds` (default 30) bounds only byte-identical repeats in an unchanged world.
- `@erc8426/issuer` (review finding): the rate limiter could be bypassed by varying the path token, since every key carried the token id or link the client chose; one client could mint nonces for unlimited token ids and evict honest pending challenges. A second bucket per family keyed by the client alone (`rateLimit.perClient`, default 120 per 60 s) now sits beside the per-token bucket; both are configurable and `perClient: false` disables the new one.
- `@erc8426/issuer` (review finding): `defaultClientKey` trusted client-controlled headers (`cf-connecting-ip`, `true-client-ip`, `x-real-ip`, `fly-client-ip`, then the first `X-Forwarded-For` hop), so a client could rotate a header to start fresh buckets or burn a victim's. It now reads only the socket address the Node adapter records. Behind a proxy, opt in by name: `forwardedClientKey(trustedHops)` takes the `X-Forwarded-For` hop that many from the right; `trustedHeaderClientKey(name)` reads one named platform header. Both fall back to the socket address. **Deployments behind a proxy must set `rateLimit.clientKey`, or every client shares the proxy's bucket.**
- `@erc8426/issuer` (review finding): a `linkSecret` change left every link and pass download dead forever. The link rows are keyed by the digest of the token the secret derives, so after a rotation (or a development restart with the ephemeral secret) the running issuer computed digests that matched no row, `fill` saw the record's links as present and minted nothing, and every link answered `unknown_capability` with nothing to heal it. Each pass record now carries `linkKeyring`, a fingerprint of the secret its bindings were written under; on load, a record stamped with another secret (or with none, as 0.3.0 records are) has its bindings rewritten under the current secret, so the holder's next claim gets working links while the URLs derived under the old secret die, as a rotation should. `rotate` and burn re-bind first so they delete the rows that exist. Records in the 0.2.x shape (raw tokens as values) heal the same way: the values become seeds, the old URLs die, the next claim works.
- `@erc8426/issuer` (review findings 4, 5, 9): a 5xx or any answer carrying `Retry-After` is never recorded for a repeat (a 503 `read_failed` on a link was replayed past its own Retry-After); `isRecordableOutcome` is exported. `POST /:tokenId/actions/:action` and `POST /:tokenId/rotate` are rate limited under their own families (`rateLimit.action` 30 per 60 s, `rateLimit.rotate` 10 per 60 s, per client and token, plus the per-client bucket), and on the signed route nothing is recorded until the nonce was spent (never for `invalid_message`, `domain_mismatch` or `nonce_invalid`), so unauthenticated garbage no longer writes repeat rows and flushes real outcomes. `memoryRepeatStore` sweeps at most once a second instead of on every write. The repeat key includes the request's `Content-Type`, since the same bytes parse differently as JSON, a form or plain text.
- Example app: the smoke script sends a distinct `attempt` per deliberate play and asserts that an identical immediate re-POST returns the same outcome with no second execution (`X-Wallet-Pass-Repeat: true`).

## 0.3.0 (every package to 0.3.0, contracts to 0.2.0)

Mainnet hardening and alignment with the current ERC-8426 draft (ethereum/ERCs PR #2036).

- `@erc8426/core`: the refusal codes follow the spec's refusal table. New codes `unknown_capability` (404), `insufficient_balance` (409) and `rate_limited` (429). `malformed_proof`, `invalid_address` and `invalid_token` collapse into `invalid_request` (400); `link_invalid` and `not_found` collapse into `unknown_capability` (404). `not_yet_valid` (401) stays and is being added to the table in PR #2036. The five retired names remain in `WalletPassErrorCode` as deprecated aliases for one minor version: `isWalletPassErrorCode` accepts them, `statusForError` maps them to the status of their replacement, and the new `canonicalErrorCode` resolves them. The issuer no longer emits them. `CANONICAL_WALLET_PASS_ERROR_CODES` lists what the SDK emits; `DEPRECATED_WALLET_PASS_ERROR_CODES` maps the aliases.
- `@erc8426/core`: `parseChallenge` reads the token and the action by position, as the spec's "Each floor field has a fixed place in the message" and the reference verifier do: the token is the first resource, the action the second. Before, it searched the resources list and refused a message with more than one of either as ambiguous. Now a message with the two swapped carries neither (the issuer refuses it as `binding_mismatch`), a message that lists the expected action anywhere but second is a proof for whatever sits second, and resources after the second are not read (the reference tolerates them; `@erc8426/client` still refuses to sign a challenge with more than two, a stricter policy on the signing side).
- `@erc8426/core`: `normalizeTokenId` (and so `tokenRef`, `assetId`, `parseAssetId` and every issuer and client entry point that takes a token id) refuses a value above 2^256 - 1 (`MAX_TOKEN_ID`), on top of the negative, fractional and non-digit input it already refused. An over-long string is refused before it is parsed.
- `@erc8426/issuer`: `createIssuer` refuses the in-memory store fallback under `NODE_ENV=production`. When `stores` leaves out `nonces`, `passes` or `links`, production throws an `IssuerConfigError` naming the missing stores (pass `kvStores(kv)`, or an explicit `memoryStores()` to run one instance deliberately); every other environment logs one warning naming the fallback, through the new `onWarning` option (default `console.warn`). `isProductionEnv()` is exported. The Apple and Google providers' own memory stores are unchanged.
- `@erc8426/issuer`: `kvStores` keys are scoped per collection. `kvStores(kv, { chainId, contract, prefix? })` now requires the chain id and contract address and writes every row under `${prefix}${chainId}:${contract}:` (contract lowercased; `prefix` still defaults to `erc8426:`): `erc8426:1:0x5f9b...c2e1:pass:412`, `...:link:<token>`, `...:nonce:<nonce>`. Two collections on one Redis, or one collection redeployed on another chain, can no longer read or overwrite each other's rows. `kvKeyNamespace(options)` returns the namespace. **Migration:** rows written by 0.2.x live under the old shape `${prefix}pass:<tokenId>`, `${prefix}link:<token>` and `${prefix}nonce:<nonce>` and are NOT read by 0.3.0. The honest migration is re-issue: deploy 0.3.x and every holder's next acquire proof creates a fresh record with new links and a new serial, so installed passes keep working only after the holder re-adds them (their old capability links answer `unknown_capability` until then). A rekey of the old rows does NOT keep links live: 0.2.x stored the link TOKEN as the record value and keyed the link rows by it, while 0.3.x stores a SEED and derives the token from it with `linkSecret`, so a renamed 0.2.x record's values are read as seeds and its old URLs die regardless. Renaming `${prefix}pass:*` rows (`RENAME erc8426:pass:412 erc8426:1:0x5f9b...c2e1:pass:412`) only preserves the record itself (serial, holder of record), and from 0.3.1 such a record heals on the holder's next claim: its bindings are written under the current secret and the new URLs work. Old `${prefix}link:*` rows can simply be deleted. Nonces need no migration (they expire within `nonceTtlSeconds`, and a nonce issued by 0.2.x is refused as `nonce_invalid` by 0.3.x, which only costs that holder a fresh challenge).
- `@erc8426/issuer`: CORS is off by default. With no `cors` option the issuer sends no `Access-Control` headers; `{ origins: "*" }` still works but must be written explicitly, and an allowlist entry must be a bare origin (scheme://host[:port]). Until 0.2.4 a wildcard was the silent default, which made every gated manifest readable cross-origin by any page the moment it held a proof. A browser-based marketplace or wallet on another origin now needs the issuer to name it or to opt into the wildcard. Deployments that serve browsers on other origins must add `cors` when upgrading; a deployment whose only browser caller is its own site needs nothing.
- `@erc8426/issuer`: every capability link page (the confirm page, its JSON form, the 404 for a dead link, the result page of a form POST, and a custom `confirmPage`) carries `Referrer-Policy: no-referrer` and `Content-Security-Policy: frame-ancestors 'none'` alongside `Cache-Control: no-store` and a new `X-Robots-Tag: noindex, nofollow` header (the HTML meta tag stays). A custom page's own CSP is kept and gains `frame-ancestors 'none'` unless it sets that directive. Exported as `LINK_PAGE_HEADERS` and `withLinkPageHeaders`.
- `@erc8426/issuer`: built-in rate limiting on the challenge, manifest and capability endpoints (GET and POST `/links/:link`, GET and HEAD `/passes/:link`), on by default: per client address and path token, 30 challenges, 60 manifests and 60 capability requests per 60 seconds, answered past the limit with 429 `{ "error": "rate_limited" }` and `Retry-After` in whole seconds. `rateLimit` configures each family (`{ limit, windowSeconds }` or `false`), the limiter (`memoryRateLimiter()` by default, an exact sliding window for one process; `kvRateLimiter(kv)` for one fixed-window limit across instances on the existing `KeyValueStore`, exact when the store implements the new optional `incr`) and `clientKey` (default `defaultClientKey`: proxy headers, then the socket address the Node adapter now records under `x-erc8426-remote-address`, dropping any client-sent value). `rateLimit: false` turns it off. `memoryKv` implements `incr`.
- `@erc8426/apple`: `validateSignerCertificate` (run by `buildPkpass` before every signing) now refuses a certificate with no subject UID (it is not a Pass Type ID certificate; until 0.2.4 such a certificate passed through), an expired or not yet valid certificate (checked against an injectable `now`, also accepted by `buildPkpass`), and a signer key that is not the certificate's own (`X509Certificate.checkPrivateKey`, with `signerKeyPassphrase` honoured). Each is a pass that would sign fine and install nowhere. New third parameter `SignerCertificateCheck` (`signerKey`, `signerKeyPassphrase`, `now`); the two-argument form still works.
- Housekeeping: every package (root, the seven `@erc8426/*` packages, `@erc8426/contracts`, the examples) declares `engines.node >=22`; CONTRIBUTING says Node 22 or newer. Versions: every `@erc8426/*` package 0.2.4 to 0.3.0 (the refusal-code renames and the KV key change are the reason for a minor bump), `@erc8426/contracts` 0.1.0 to 0.2.0; internal ranges stay `workspace:^`. Licence check: root LICENSE, every `package.json`, every `.sol` SPDX header and every package README say MIT, with the ERC text itself CC0, as the root and contracts READMEs state; nothing disagrees.
- Proof headers renamed per RFC 6648 (ethereum/ERCs PR #2036): `Wallet-Pass-Proof` and `Wallet-Pass-Signature` replace `X-Wallet-Pass-Proof` and `X-Wallet-Pass-Signature`. `@erc8426/core`: `PROOF_HEADER` and `SIGNATURE_HEADER` carry the new names; `LEGACY_PROOF_HEADER` and `LEGACY_SIGNATURE_HEADER` (deprecated) the old; `PROOF_HEADER_NAMES` lists all four. `readProofHeaders` reads the new name first and the X- name when the new one is absent, so the new name wins when both are present. `proofHeaders` sends BOTH sets for this release (`{ legacy: false }` sends only the new), so a 0.3.0 client (and `@erc8426/conformance`) still resolves a 0.2.x issuer's manifest; **the X- names will stop being sent in a later minor**, after which a 0.2.x issuer must be upgraded. `@erc8426/issuer` accepts both and lists all four in the CORS preflight.
- Manifest `version`: `PassManifest` gains an optional integer `version` (1, `MANIFEST_VERSION`); `createManifest`, and so every `@erc8426/issuer` manifest, emits `"version": 1`. `parseManifest` (and so the client) tolerates its absence, refuses a non-integer, and warns on a value above 1. The manifest MUST be served as `Content-Type: application/json`: the issuer always did; `@erc8426/conformance` now checks it (`manifest.media-type`, `gated.manifest.media-type`).
- `@erc8426/issuer`: an identical repeat is not a replay (spec revision). `POST /links/:link` is keyed by link and a SHA-256 of the body; `POST /:tokenId/actions/:action` by nonce, message, signature and body. An identical request arriving while the first is in flight awaits the same execution; one arriving within `repeat.windowSeconds` (default 30) after completion gets the recorded status and body (marked `X-Wallet-Pass-Repeat: true`). A different body on the same link is a new request; a different request carrying a spent nonce is still `nonce_invalid`; every completed outcome is recorded, refusals included (a repeated refusal repeats, never as `nonce_invalid`), and on the capability path the link is resolved before the repeat store is consulted and the key carries its binding and holder, so a recorded answer is never served for a rotated or re-claimed link. Default store `memoryRepeatStore()` (bounded, one process); `kvRepeatStore(kv)` shares completed outcomes across instances through the existing `KeyValueStore` with TTL (requests still in flight are shared within one process only). `repeat: false` disables.
- `@erc8426/issuer`: explicit `environment: "production" | "development"` on `createIssuer`. When set it decides the production guards (today the in-memory store refusal); `NODE_ENV` is only the fallback when it is unset. When neither is set and `chainId` is a known mainnet (`MAINNET_CHAIN_IDS`: 1, 10, 137, 8453, 42161; `isKnownMainnet`) the issuer logs one warning that production mode is undetermined and names the option, without refusing. `ResolvedIssuerConfig.environment` reports `"production"`, `"development"` or `"unknown"`; `resolveEnvironment` is exported.
- `@erc8426/issuer`: a read of the store yields no usable capability (spec revision, Security Considerations). Link records are keyed by the SHA-256 digest of the token from 0.3.0, the pass record holds a random seed per link and download, and the token in a holder's URL is `HMAC-SHA256(linkSecret, seed)`, derived again on every render and hashed before every lookup. New `linkSecret` option (at least 32 bytes, the same on every instance), REQUIRED in production; development without it gets a random per-process secret and a warning (links then die with the process). `LinkStore` is keyed by digest; `LinkKeyring`, `linkDigest`, `newLinkSeed`, `ephemeralLinkSecret` are exported. No dual lookup: 0.3.0 already does not read 0.2.x rows. Nonces stay stored as issued: single-use, short-lived, and worthless without the holder's signature. The example app reads `ISSUER_LINK_SECRET`.
- `@erc8426/google`: Android view constraints as typed options. `view: { screenshots?: "allow" | "refuse"; unlockToView?: boolean; nfcBlock?: ("payment" | "closedLoopTransit")[] }` on `googleFormatProvider` (and `MappingOptions.view`, `ClassOptions.view`) emits `passConstraints.screenshotEligibility` (ELIGIBLE or INELIGIBLE) and `passConstraints.nfcConstraint` (BLOCK_PAYMENT, BLOCK_CLOSED_LOOP_TRANSIT) on every object, superseded and expired ones included, and `viewUnlockRequirement` (UNLOCK_REQUIRED_TO_VIEW or UNLOCK_NOT_REQUIRED) on the class. Left out, nothing changes. `passConstraintsFor` and `viewUnlockRequirementFor` are exported. Apple Wallet has no equivalent.
- `@erc8426/google`: signed save and delete callback verifier. `createCallbackVerifier({ issuerId, fetchKeys?, fetch?, keyCacheSeconds?, now?, nonceStore?, onWarning? })` verifies Google's ECv2SigningOnly envelope as Tink's PaymentMethodTokenRecipient does for sender `GooglePayPasses` and recipient = the issuer id (root keys from `https://pay.google.com/gp/m/issuer/keys`, cached by max-age; intermediate key signature and expiry; message signature; message expiry; optional nonce deduplication on a `KeyValueStore`-shaped store with a TTL to the message expiry; advisory User-Agent check). `callbackHandler(verifier, onEvent)` is the fetch handler (200 verified, 400 never-verifies, 503 keys unavailable or handler threw, 200 redelivered nonce). Exports `toSignedString`, `memoryCallbackNonceStore`, `maxAgeOf`. No Node adapter of its own: use `toNodeHandler` from `@erc8426/issuer`.
- `@erc8426/core`, `@erc8426/apple`: Apple Featured Actions (iOS 27). `PassContent.featuredActions` takes up to two `{ id, type, url }` or `{ id, type, link }` entries (`FeaturedAction`, `FeaturedActionType` with Apple's documented types, `MAX_FEATURED_ACTIONS`); `toPassJson` emits the top-level `featuredActions` array (`identifier`, `type`, `url`), resolving a `link` reference to the URL of the content's link with that key at render time so a capability link rotates with the pass. More than two, a duplicate id, a missing type, a non-https or scheme-less URL, or an unknown link reference is refused. Voided content drops the entries that point at links; `supersededContent` carries none. Older iOS and Google ignore the key. `featuredActionsFor` is exported.
- `@erc8426/issuer`: every 400 for a malformed address, token id or proof header is `invalid_request`; every 404 (a rotated or unknown link, a download link, a nonexistent token in the public configuration, an unknown route) is `unknown_capability`.
- `@erc8426/client`: a code from a 0.2.x issuer is reported under the spec's name (`malformed_proof` arrives as `invalid_request`) with the string the issuer sent in `serverCode`. A reverted `passURI`, `tokenURI` or `ownerOf` read (a token that does not exist or was burned) is now `unknown_capability` with `source: "chain"`, where it was `not_found`; a 404 with no recognizable body is `unknown_capability` too. `@erc8426/react`'s `describeError` wording follows.

## 0.2.4 (google; every package republished at 0.2.4)

Android notifications, from the WALLETCHI deployment (2026-10-19): the provider sent every Google Wallet message as `TEXT`, which only shows inside the saved pass, so Android holders were never notified of a deadline reminder.

- `@erc8426/google`: `GoogleMessage` gains `notify?: boolean`. `addMessage` sends `messageType: TEXT_AND_NOTIFY` when it is set, which is the only kind that raises an Android notification; the default stays `TEXT`, so 0.2.3 behavior is unchanged and superseded messages stay silent. Google caps notifying messages per object per day (three at the time of writing).
- Docs: `docs/platforms/google.md` says which message kind notifies; `docs/platforms/apple.md` records the one-banner rule (a notifying update whose only visible change is the value of one existing field with `changeMessage`), that a value change to a repeated `posterGeneric` key raised one message on iOS 27, and that dropping a `changeMessage` is silent.

## 0.2.3 (apple, google; every package republished at 0.2.3)

Registration cap without eviction, from Nexory's review of the WALLETCHI PassKit web service (2026-10-15), which found that 0.2.2's eviction rule lets a forwarded pass push the holder's devices out.

- `@erc8426/apple`: at `MAX_REGISTRATIONS_PER_PASS` live devices a NEW device is refused (the web service answers 403); no registered device is ever evicted. Under 0.2.2 anyone holding a copy of the current pass (a forwarded file or mail) could register ten devices and silently cut the holder's own devices off updates. A device already registered still re-registers at the cap.
- `@erc8426/apple`: `DeviceRegistrationStore.register` may return `"full"` (the type widens to `Promise<boolean | "full">`; a store returning a boolean still compiles, but MUST stop evicting). New REQUIRED `supersede(passType, serial)`: the provider calls it whenever a pass's token rotates (transfer, voided supersede, `rotate()`). Superseded registrations still answer the device's list call and get pushes for `SUPERSEDED_PUSH_WINDOW_MS` (24 h), so the old pass refreshes into its superseded rendering, but they no longer count toward the cap, so an owner's rotation always frees the slots a forwarded copy filled. Custom stores must implement `supersede()`; without it the cap would lock owners out after a rotation (a forwarded copy that filled the ten slots would keep them forever, and the owner's new pass would answer 403 on every device). `MemoryApplePassStore` implements both; `pushPassUpdate` now sends to at most `MAX_PUSH_TOKENS_PER_PASS` (20: the live set plus as many superseded).
- `@erc8426/apple`: the provider calls `supersede()` BEFORE it persists the rotated record, on both the sync path (transfer, voided supersede) and `rotate()`. A supersede that throws now leaves the rotation unpersisted and retried on the next call; the other order would have persisted the rotation and left the old devices holding the slots with nothing to retry it. `supersede()` is idempotent, so a putPass failure after it is harmless.
- `@erc8426/apple`: the web service answers 403 at the cap, a status outside the 200/201/401 Apple documents for registration; the pass installs on that device but never updates (documented in `docs/platforms/apple.md`).
- `@erc8426/google`: expiring a superseded object retries once, and only on a transient failure (a 5xx, a 429, or no HTTP answer at all); a definite answer such as 404 is reported once and not retried. The provider forgets the old object id once the call returns, so an expire that never landed left every saved copy ACTIVE with nothing able to retry it.
- Example app: the Redis store keeps a live list (claimed atomically by a Lua script, so concurrent registrations never land past the cap and a device registering twice at once lands once) and a sorted set of superseded devices. Registrations written by 0.2.0 and 0.2.1 (the hosted demo), which have neither, keep receiving pushes through the per-serial token set and keep their slot when they next register. Covered by `examples/next-app/test/kv.test.ts` against an in-memory Upstash fake.

## 0.2.2 (apple; every package republished at 0.2.2)

Bounded Apple Wallet registrations, from a review of WALLETCHI's PassKit web service by Nexory (2026-10-14). No API changes.

- `@erc8426/apple`: a pass keeps at most `MAX_REGISTRATIONS_PER_PASS` (10) registered devices. `MemoryApplePassStore` evicts the least recently registered device; a device re-registering counts as fresh and evicts nobody. Every update sends one APNs request per token, so an unbounded set let anyone holding a pass make each push arbitrarily expensive. `DeviceRegistrationStore` now documents the cap as a MUST for custom stores, and `pushPassUpdate` sends to at most that many tokens even if a store does not enforce it.
- `@erc8426/apple`: the web service answers 400 for a device library identifier that is longer than 64 characters or not path-safe.
- Example app: the Redis store keeps a per-pass recency list and evicts past the cap.
- `@erc8426/contracts` (comment only, not republished): `StoredValueCard` notes that in a token-bound variant an approval granted from the card's own account survives a transfer, and that a production account should refuse approvals and allow only revocations.

## 0.2.1 (core, client, conformance; every package republished at 0.2.1)

Three fixes from an outside security review (Nexory, 2026-10-14). No API changes.

- `@erc8426/client`: redirects are followed by hand, at most three, and every hop must pass the same https (or loopback http) check as the first URL. Before, `fetch` followed them unchecked, so an allowed URL could bounce the client to `http://169.254.169.254/` or any plain-http host. In a browser, where a manual redirect comes back opaque, a GET is asked once more and the browser follows it itself: only the final URL is checked (https, or loopback http), and the body is dropped if it fails; any other method is refused. Regression tests in `audit-regressions.test.ts`.
- `@erc8426/conformance`: the owner key no longer signs whatever challenge the server under test returns. Before signing, the run applies the check `@erc8426/client` uses (`checkChallengeScope`): the challenge must come from the origin that serves the manifest and name that host, this token, the owner's account and the acquire action, with an Expiration Time inside the default lifetime limit. Otherwise nothing is signed and the owner checks are skipped with the reason. A server that issues challenges naming another host, or a lifetime above one hour, now gets its owner checks skipped instead of run.
- `@erc8426/core`: `parseChallenge` refuses a message longer than `MAX_CHALLENGE_MESSAGE_CHARS` (4096) before parsing it. The SIWE parser is quadratic on repeated `URI: ` without a newline (about 600 ms at 64 KiB), and an issuer parses before it knows the caller. A conforming challenge is under 2 KiB. Reported by Nexory (2026-10-14); the parser itself is being reported upstream to viem.

## 0.2.0 (published 2026-10-09)

Apple's iOS 27 Poster Generic face, and a signing-time check that the certificate matches the pass.

- `@erc8426/core`: `PassStyle` gains `"posterGeneric"`; `PassContent` gains `footer`, `posterFallback` and the `artwork` and `primaryLogo` image slots.
- `@erc8426/apple`: `posterGeneric` emits two dictionaries on one pass, the poster (one header field, up to four primary, one footer, the back) and a legacy fallback (`posterFallback`, default `generic`) with the full field set, so iOS 26 and earlier render the legacy layout. More fields than the poster face shows throws, as a duplicate key already did; a footer on another style throws. Images ship for both faces. Needs passkit-generator 3.6 or later at signing (the range already resolves 3.6.1); 3.5 strips the `posterGeneric` key silently.
- `@erc8426/apple`: `buildPkpass` refuses a signer certificate whose subject UID is not the `passTypeIdentifier` or whose OU is not the `teamIdentifier` (`validateSignerCertificate`). Such a pass signs fine and installs nowhere. Test certificates now carry Apple's UID and OU attributes.
- `@erc8426/google`: `posterGeneric` maps to the generic vertical; the portrait `artwork` is not used as the wide Google hero.

## 0.1.1 (issuer, core, apple, google)

Superseded passes say why. ERC-8426 now asks that a pass presented as superseded state why and, where its holder may still be the owner, how to get the replacement (ethereum/ERCs PR #2036, de989060, raised on the Magicians thread).

- `@erc8426/core`: `SupersededReason` (`"transfer" | "reset"`) and `PassContent.supersededReason`.
- `@erc8426/issuer`: the old serial is pushed with `supersededReason` (`"reset"` for the owner's rotation, `"transfer"` for an observed transfer or a new account's claim), and `render` receives it.
- `@erc8426/apple`: the default superseded pass reads "Transferred" or "Links reset" and names the issuer to get the current pass from; each retired token remembers its own reason (`retiredReasons`, `retiredReasonFor`), and `supersede(content, reason)` receives it. Records from 0.1.0 load and render the generic wording.
- `@erc8426/google`: the superseded message follows the reason (`defaultSupersededMessage`); `supersededMessage` also accepts a function of the reason.
- Example renderers say "Links reset" on a reset instead of "Transferred".

Found by running the example app on Vercel from the published 0.1.0 packages:

- `@erc8426/issuer`: `kvStores` now accepts a key-value client that parses JSON on read. The `@upstash/redis` shim in the 0.1.0 README used the client's default automatic deserialization, which handed `kvStores` objects instead of strings, so every gated request failed. The README shim now turns that off, and `kvStores` works either way (regression test in `stores.test.ts`).
- `@erc8426/core`: ships its README (0.1.0 listed one in `files` that did not exist).
- Example app: hosted mode for serverless (shared Upstash stores for the issuer, Apple and Google; a cross-instance operator lock and nonce; log catch-up in place of watchers; rate-limited mint; an opt-in testnet burner wallet and gas drip), and the smoke test now fails, instead of skipping, when the conformance package is missing, and runs against a deployed instance.
